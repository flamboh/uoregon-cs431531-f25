\section{Implementation}
A simple MPI interface made this work for distributing the computation across MPI ranks. I also wrote two helper scripts:
\begin{itemize}[leftmargin=*]
  \item \texttt{parse\_timings.py} extracts the ``Module / Time'' section from each run and emits comma-separated values ordered by stage.
  \item \texttt{aggregate\_timings.py} batches all \texttt{out/*cpu.out} files, averages the timings per thread count, and appends the thread count (parsed from the filename) as a new \texttt{num\_threads} column.
\end{itemize}
The aggregated CSV (\texttt{output/thread\_scaling.csv}) feeds both the discussion and plots below. Each MPI batch ran on the \texttt{cant} matrix with thread counts $\{1,4,8,16\}$ using the provided Talapas job script.

\section{Measurement Methodology}
After collecting five clean runs per configuration, $aggregate\_timings.py$ averaged the rows into a single summary per thread count. Timing variability across runs stayed within 2\% for each stage, so the mean captures the trend accurately.

\section{Results}
\subsection{COO Kernel Scaling}
Figure~\ref{fig:coo_line} shows the averaged COO timing reported by the MPI harness. Moving from one to four threads cuts the local SpMV to $6.7$ ms because the MPI ranks simultaneously work through their row blocks. Beyond eight threads the curve flattens near $2$ ms: each rank receives so few rows that threading overhead rivals useful work. The measurements confirm that the COO kernel provides limited scaling opportunity once communication and preprocessing dominate.

\subsection{Effect on End-to-End Runtime}
Even though the COO stage is short, its reduction still matters when sweeping thread counts. Comparing the totals derived from \texttt{aggregate\_timings.py} shows a $3.8\times$ drop in overall runtime (7.73 s $\rightarrow$ 0.91 s) between one and sixteen threads. Only about 6--8 ms of that savings comes from the COO kernel itself, so the primary benefit of optimizing COO is preventing it from becoming a bottleneck as the rest of the pipeline accelerates. The helper scripts make it easy to keep watching the COO contribution in future experiments with different matrices or hybrid formats.

\section{Conclusions}
The measurements highlight that the MPI pipeline already spends the vast majority of its time before and after the COO kernel. Either way, the kernel scales from $4.3$ ms down to $2.0$ ms as we increase threads, ensuring that it stays hidden behind I/O and communication costs. It would have been good to include additional tests on more nodes. However there were none available. Overall, these results make reasonable sense, particularly for a matrix this size. The scale is not large enough to amortize much of the costs of MPI. Though resulst for multithreading here were far more consistent with expecations than that of many of my previous assignments. Hard to tell if this is a change with Talapas or a fix in my own understanding, but nonetheless good to see.
